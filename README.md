# Retail Medallion Pipeline: agentic Bronze, Silver, Gold and report

An agentic workflow that ingests messy raw retail sales CSVs, cleanses them through a
Medallion architecture, aggregates them into analytics tables, and writes an executive report.
A Supervisor agent coordinates six sub-agents. A human approves each source-to-target mapping (STTM) before the layer
that depends on it runs.

Built for the *Accelerate with AI* training use case: **Data Engineering: Retail Medallion Pipeline & Reporting**.

## How it works

```
raw CSVs ──► Profiler ──► STTM (Bronze) ──► ⏸ approve
                                              │
            Bronze agent ──► STTM (Silver) ──► ⏸ approve
                                              │
            Silver agent ──► STTM (Gold) ───► ⏸ approve
                                              │
            Gold agent ──► Reporter ──► HTML report + JSON
```

| Agent | Module | Job | Tools |
|---|---|---|---|
| Supervisor (Orchestrator) | `agents/orchestrator.py` | Phase order, approval gates, handoff, output checks, audit | Sub-agents as tools |
| Data Profiler | `agents/profiler.py` | Column stats, semantic types, join keys, quality notes; PII masked | `inspect_files_tool`, `profiler_tool` |
| STTM | `agents/sttm_generator.py` | Proposes Bronze, Silver and Gold mapping rules for review | `inspect_context_tool`, `generate_sttm_tool` |
| Bronze | `agents/bronze_agent.py` | Raw CSV to Parquet, values unchanged, lineage columns added | `inspect_task_tool`, `bronze_ingestion_tool` |
| Silver | `agents/silver_agent.py` | Cleanse: currency, types, dates, blanks, negatives, dedupe, surrogate key | `inspect_task_tool`, `silver_ingestion_tool` |
| Gold | `agents/gold_agent.py` | Joins, group-bys and aggregates into analytics tables | `inspect_task_tool`, `gold_ingestion_tool` |
| Reporter | `agents/reporter.py` | Read-only SQL over Gold, executive summary, charts | `inspect_gold_tables_tool`, `load_gold_data_tool`, `execute_query_tool` |

Each agent runs a ReAct loop (THINK, INSPECT, PLAN, ACT, VERIFY) built with LangChain `create_agent`.

### Phases

| Phase | Runs | Stops at |
|---|---|---|
| 1 | Profiler, Bronze STTM | Human approves Bronze STTM |
| 2 | Bronze ingestion, Silver STTM | Human approves Silver STTM |
| 3 | Silver cleansing, Gold STTM | Human approves Gold STTM |
| 4 | Gold materialisation, Reporter | Complete |

After every phase the Supervisor checks each promised output exists on disk. A sub-agent's
"success" message is never enough by itself.

### Handoff

- **Within a phase:** a plain dict, the *scratchpad*, is shared by the tools in that phase.
- **Between phases:** `PipelineState` is saved to `data/runs/<run_id>.json`. The scratchpad is copied into it, then discarded.

## Quick start

Tested on Python 3.13 with Windows 11.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
```

**Offline run, no API key needed.** The same steps run as plain code:

```bash
python cli.py --deterministic --auto-approve
```

**Agentic run.** Copy `.env.example` to `.env`, add your key, then:

```bash
python cli.py
```

The run pauses at each approval gate. Resume a paused run with `python cli.py --resume <run_id>`.

**UI with human approval:**

```bash
streamlit run streamlit_app.py
```

Upload CSVs or use the bundled sample data. Edit the `include` column in the STTM grid (Y/N), then approve.

**Tests:** `python -m pytest -q` (35 tests). None need a network or an API key. The LLM path is exercised with a scripted fake model that checks wiring, gates, traces and output verification. It does not measure model quality. That needs a live run with your key.

## Sample data

`sample_data/` holds **synthetic** Retail Co CSVs, generated by `scripts/generate_sample_data.py` (seeded).
They are deliberately messy so the agents have real problems to solve:

- mixed date formats (`2026-03-05`, `05-Mar-2026`, `03/05/2026`)
- currency symbols and thousands separators in amounts
- blank and text quantities (`""`, `"two"`), negative quantities
- exact duplicate rows
- region and category casing or whitespace variants
- orphan `product_id` values with no matching product
- blank `customer_id` values

Use your own CSVs with `--files` or the UI. Each file's name becomes its dataset name (`sales_raw.csv` becomes `sales`).
The Gold templates expect `sales`, `customers` and `products`. Any other file is profiled and cleansed but not aggregated.

## Safety and data handling

- **No code generation from the model.** STTM transformations are names from a whitelist (`core/sttm.py`). Unknown names are rejected when the STTM is read, so an edited or generated rule cannot run arbitrary code.
- **Data minimisation.** The LLM receives profile statistics and sample values. PII columns (name, email, phone, address) are masked before anything leaves the process.
- **Read-only reporting.** Reporter SQL must be a single `SELECT` or `WITH`. Write and DDL keywords are blocked.
- **Fixed charts.** The LLM does not choose chart queries. They are reviewed SQL in `agents/reporter.py`.
- **Audit and traces.** `data/audit/` and `data/traces/` record decisions, file names and counts. They never record data values.
- **Keys.** Keys come from `.env`, which is git-ignored. Use the firm's approved provider accounts only.

## Outputs

| Folder | Contents |
|---|---|
| `data/profiles/` | `profile_combined_<date>_<run>.json` |
| `data/sttm/` | `sttm_{bronze,silver,gold}_<run_id>.csv` (review and approval copy) |
| `data/bronze/<run_id>/` | `<dataset>_bronze.parquet` |
| `data/silver/<run_id>/` | `<dataset>_silver.parquet` (surrogate key `pk_<dataset>_silver_id` first) |
| `data/gold/<run_id>/` | One Parquet file per Gold table |
| `data/reports/` | `report_<run_id>.html` (charts work offline), `report_<run_id>.json` |
| `data/traces/` | `trace_<agent>_<run[:8]>.json` (agent plan, tool calls, reasoning chain, duration) |
| `data/audit/` | `audit_<run_id>.jsonl` |

Outputs are grouped per run, so runs never overwrite each other. `data/` is git-ignored.

## Design decisions

- **Tool factories with closures.** Each agent's tools capture the run's file paths, STTM path and scratchpad when created. The LLM only supplies a goal, so it cannot make up file paths.
- **Deterministic core under every agent.** The data work lives in plain functions, so the pipeline is testable offline, reproducible, and still works if the LLM fails. Agents decide *how* to call the work and *what to say about it*.
- **Human gates are data, not prompts.** Approval is a state change that validates the edited STTM file. A model cannot approve its own rules.
- **Charts from fixed SQL, narrative from the LLM.** The numbers in the report are reproducible. The LLM adds reasoning, not figures.

### Where this differs from the deck

| Deck | This build | Why |
|---|---|---|
| ChromaDB memory store | JSON-file document store (`core/memory.py`) | No extra service for the first version. The interface is small enough to swap later. |
| Output folders flat under `data/` | Per-run subfolders | Repeated runs do not overwrite each other. |
| Silver `dropna` and `fillna` on the whole table | Per-column rules | Lets the human approve each column's handling. |
